# FDE2E Photocraft in the browser and WebMCP

The complete Rust editor runs locally in WebAssembly: documents and pixel processing do not
go to a server. WebGPU renders the canvas where available, with WebGL2 as the fallback. The
web shell registers WebMCP tools automatically once the editor starts.

## Run

```sh
rustup target add wasm32-unknown-unknown
brew install trunk                 # alternatively: cargo install trunk --locked
cd apps/photocraft-web
trunk serve --release              # http://127.0.0.1:8765/
```

For a distributable static site, run `packaging/web/package.sh` from the repository root.
The zip in `dist/` contains the app, streaming loader, compressed Wasm parts and hosting
instructions. Serve it over HTTPS (localhost HTTP also works). There is no Node.js or backend
runtime. The only shipped JavaScript is generated by wasm-bindgen/Trunk. See
[hosting](../packaging/web/README.md) for compression, MIME types, caching, subpaths and Docker.

### Background-worker build

The compatibility build above does not require cross-origin isolation. For CPU-heavy editing,
build the shared-memory variant as well:

```sh
rustup toolchain install nightly-2026-08-17 --profile minimal --component rust-src
PHOTOCRAFT_WEB_THREADS=1 packaging/web/package.sh
```

`packaging/web/build-threaded.sh` rebuilds the Rust standard library with atomics and bulk
memory and enables the app's `threads` feature. The worker runtime is the pinned
`wasm-bindgen-rayon` 1.3.0 dependency; no handwritten JavaScript or new UI framework is shipped.
The linker must use both `--shared-memory` and `--import-memory` with a bounded maximum memory.
Atomics alone do not make the memory shared on this toolchain. The script generates a temporary
HTML entry point with `heif,threads`: Trunk's HTML `data-cargo-features` overrides its CLI feature
flag. The app's Rust build script retains the required TLS initializer/globals at final linking.
The build rejects output without worker exports or an explicitly shared memory initializer.
It creates two to four reusable workers, reserving a logical CPU for the browser where possible.
An HTTPS or localhost host must send `Cross-Origin-Opener-Policy: same-origin` and
`Cross-Origin-Embedder-Policy: require-corp`; the bundled `_headers` and `.htaccess` include them.
Fonts and other fetched resources must be same-origin or satisfy CORS/CORP.

The packaged streaming loader selects `app-threaded/` only when the page is isolated and its
worker parts are present, otherwise it selects the compatibility `app/` build. A worker startup
failure is reported rather than silently losing background execution. The app reports the actual
runtime with `window.photocraft.backgroundWorkers`. Direct Trunk worker builds require these
headers too; ordinary `trunk serve` is not an isolated host.

## Agent tools

PhotoCraft supports the [current WebMCP draft](https://webmachinelearning.github.io/webmcp/)
on `document.modelContext` and the earlier `navigator.modelContext.registerTool` API.
Availability depends on the browser and its WebMCP settings. Tools use the page's origin;
PhotoCraft does not opt into exposing them to other origins.

| Tool | Arguments | Result |
|---|---|---|
| `photocraft_commands` | `search?`, `offset?`, `limit?` (1–200; default 50) | Command IDs, semantic descriptions, `inputSchema`, coverage, current enablement, total matches and next offset |
| `photocraft_execute` | `command`, `params?` | Execute any engine/UI command in the visible session, sharing undo history |
| `photocraft_inspect` | `{}` | Documents, layers, selection, history, tools, dialogs, GPU path, memory and frame timings |
| `photocraft_control` | `method`, `params?` | UI menus/dialogs, pointer/pen/keyboard input, screenshots, jobs and browser saves |
| `photocraft_import` | `name`, `base64` | Open image/project/preset bytes, returning warnings and document state |
| `photocraft_export` | `name`, `quality?` (1–100), `download?` (default false) | Export bytes as base64 or trigger a browser download; returns format warnings |

Six tools expose the whole evolving command registry through discovery and dispatch. New
engine commands need no duplicate registration. This keeps tool discovery small and avoids
thousands of callbacks or a huge command list in every agent context. Search, then page using
`nextOffset`; `null` means the end. Use `ui.menu.list` for shell-only menu actions. The control
tool's JSON Schema lists all browser-supported protocol methods; their parameters are in the
[control protocol](control-protocol.md).

On the current API an in-page agent can discover and invoke tools as follows (client example;
the implementation is Rust):

```js
const context = document.modelContext;
const tools = await context.getTools();
const execute = tools.find(tool => tool.name === "photocraft_execute");
const response = JSON.parse(await context.executeTool(execute, {
  command: "file.new",
  params: { width: 1600, height: 1200, depth: 16, name: "Browser project" }
}));
```

Responses use the editor's `{ok: true, result: ...}` or `{ok: false, error: ...}` envelope.

### Structured error diagnostics

Application-controlled failures preserve the string `error` for existing integrations and
add `errorInfo`. Argument validation happens before queue admission or editing:

```json
{
  "ok": false,
  "error": "/limit: maximum is 200",
  "errorInfo": {
    "code": "INVALID_ARGUMENTS",
    "message": "/limit: maximum is 200",
    "execution": "not_started",
    "retrySafe": true,
    "hint": "Correct the indicated field using the tool inputSchema, then retry.",
    "path": "/limit",
    "expected": {"type": "integer", "minimum": 1, "maximum": 200, "default": 50}
  }
}
```

`path` is a JSON Pointer (empty for the root). `expected` contains the relevant constraint;
semantic filename, UTF-8 byte and decoded-file limits may use diagnostic keys such as
`maxBytes` or `maxDecodedBytes`, rather than a complete JSON Schema. Neither field is
required for execution/transport failures.

| `errorInfo.code` | Meaning |
| --- | --- |
| `INVALID_ARGUMENTS` | Invalid envelope, field, filename or encoded file; no dispatch |
| `UNKNOWN_TOOL` | No registered tool with that name; no dispatch |
| `REQUEST_TOO_LARGE` | Request exceeds the browser transport limit; no dispatch |
| `QUEUE_FULL` | Queue admission failed; wait for an outstanding request |
| `REQUEST_INTERRUPTED` | Aborted/expired before dispatch, or a worker result was discarded |
| `EXECUTION_UNCERTAIN` | Aborted/expired after control dispatch; changes may still apply |
| `EXECUTION_FAILED` | Editor/file operation failed; inspect before replaying |

`execution` is `not_started`, `not_applied` (discarded worker result), or `unknown`.
`retrySafe` only describes duplicate-edit safety, not whether unchanged arguments will
succeed or whether the agent should retry automatically. Correct invalid arguments first.
An ordinary engine error is conservatively `unknown`, because an operation can fail after
some state has changed. Existing error response fields are retained.

These failures resolve to the error envelope rather than intentionally rejecting the tool
callback's Promise. The browser can still reject a native WebMCP invocation *before* the
callback runs (for example its own input-schema validation), and transport failures can
still reject. For a generic browser `UnknownError`, use the non-mutating same-page diagnostic:

```javascript
window.photocraft.validateTool("photocraft_commands", {limit: 300})
```

It synchronously returns the same argument-error envelope, or
`{ok: true, result: {valid: true}}`. It shares parsing and size limits with the actual
callback, never queues a request or edits a document, and does not echo submitted payloads.
A successful validation checks the tool envelope and its browser-specific semantics, **not**
the engine command's parameters, enabled state or eventual execution outcome. Continue to
discover command schemas before editing. This helper does not replace native WebMCP execution.

The phased reliability work and remaining acceptance gates are tracked in
[WebMCP reliability](webmcp-reliability.md).

### Discovering commands

Invalid tool arguments fail before editing. Do not infer success from a
resolved promise alone: check `ok`. A disabled or unsupported command returns an error.
Every engine command entry now includes a draft 2020-12 JSON Schema in `inputSchema`,
alongside a semantic `description` and `journal` flag. The legacy `params` string remains
for compatibility; it is JSON-like prose, **not** a schema. Construct execute arguments
from the discovered entry's `inputSchema`, rather than attempting to parse `params`.

### Command contracts and migration coverage

The six tools are stable transport envelopes. `photocraft_execute.params` deliberately
remains a generic object because its contract depends on the chosen command ID. Search
`photocraft_commands` for the operation, read that entry's schema, then execute its exact
ID. There is no second registry of hundreds of WebMCP tools to drift from the engine.
The engine, CLI, MCP server, control channel and browser all share these command entries.

Check `inputSchema["x-photocraft-coverage"]` before treating a contract as complete:

- `complete`: an explicitly authored parameter catalogue, including documented nested
  forms, required fields, constraints and semantics, or a contract derived from the same
  typed rules used by execution. The engine still checks document-dependent constraints
  such as existing layers, masks, installed fonts/profiles, locks and geometry budgets.
- `partial`: conservative legacy-documentation conversion or a partly verified override.
  Unknown nested fields may remain open, and required fields, aliases or variants may be
  missing. The schema's `$comment` makes this limitation explicit. Partial schemas are
  guidance, not grounds for rejecting an existing valid call. This is **not yet complete
  coverage of the entire command registry**.

These are authoring contracts: defaults describe omission; they are not inserted into
requests by the transport. Historical coercions and ignored unknown keys in older engine
commands are not a recommendation to send arbitrary values. The migration does not add
schema-based dispatch rejection or change existing command execution behavior. `file.new`
has a closed parameter validator and, unlike most commands, does not accept `coalesce`
or `target`. Other commands only honor a pixel-edit `target` where their operation supports
it; an existing command-specific `target` property keeps its own meaning.

The verified contracts cover core inspection/history, vector-shape creation/editing,
Bézier paths, common layer operations, text creation/editing/formatting, marquee selection,
bucket/gradient painting, Free Transform, Filter Gallery effects and strictly validated
filters. Nested `BrushSettings`, `paint.stroke`, brush inspection/settings and common preset
operations are now audited, as are `edit.fill`, `layer.duplicate`, `image.imageSize` and
`image.canvasSize`. The production registry has **135 complete and 829 partial contracts**
out of 964 commands; other legacy families remain migration work, not silently certified
contracts. Formal output schemas and per-command browser capability annotations remain separate work.

### Nested brush settings

Discover `tools.setBrush` or `paint.stroke` to obtain self-contained `$defs` for dynamics,
controllers, response curves, scattering, texture patterns, sampled/stored tips, dual brushes,
colour dynamics, transfer, pose, smoothing, section locks and mixer settings. `$ref` values are
local to the returned command schema; no network schema resolution is needed. Enums reuse the
actual Rust variants and tests walk serialized settings to catch undocumented fields.

- Every brush object is a **deep patch**. Omitted fields retain the current/preset value;
  arrays replace their old value. Factory values used by `reset` live in
  `$defs.BrushSettings["x-photocraft-initial-default"]`, not `default`: inserting initial
  values into a patch would silently reset user settings. They need not match the live
  session brush; use `brush.get` to inspect it.
- `tools.setBrush`: current brush → preset pick (preserving section locks and smoothing) →
  `reset` if requested → nested `brush` patch → root-level BrushSettings fields. It changes
  the tool, not document pixels. A reset clears the current preset identity.
- `paint.stroke`: current brush → preset pick → nested `brush` patch → scalar overrides.
  Colour/background come from top-level `color`/tool colours, `erase` defaults to false,
  and `seed` comes from the top level or is derived from points: these replace their nested
  counterparts even when the top-level key is omitted. Stroke overrides do not persist the brush.
- Changing a dynamics child does not enable its section. Set `enabled:true` where needed;
  pose additionally needs the relevant override flag, texture depth jitter needs `eachTip`,
  and temporal buildup/catch-up needs sample timestamps. Nested `mode` is the exact serialized
  variant (`"Multiply"`), unlike the case-insensitive top-level blend name (`"multiply"`).
- Nested colour arrays are exactly four RGBA fractions. Mixer settings are fractions 0–1,
  whereas `paint.mixerBrush` top-level numeric controls use percentages. The latter command
  is still partial; discovering one complete nested type does not certify every brush tool.
- Same-variant bitmap/pattern patches may omit existing fields; changing enum variant needs
  a complete new payload. Tile sample counts must equal width × height, checked at runtime.
  Stored bitmap keys are device/store references, not portable URLs; use embedded sampled
  tips for portability. Other state-dependent limits still apply.

For example, configure a reusable pressure-sensitive brush without painting:

```json
{"command":"tools.setBrush","params":{"size":12,"shapeDynamics":{"enabled":true,"size":{"control":"penPressure","minimum":0.2}},"scattering":{"enabled":true,"scatter":{"jitter":1.5}}}}
```

Artistic planning, composition and visual review belong in reusable agent skills, not
image-specific command branches. These contracts improve general tool invocation; they do
not generate illustrations or guarantee artistic quality.

Descriptions distinguish document pixels from UI points, `[x,y,width,height]` from
`[x0,y0,x1,y1]`, opacity fractions from percentages, text points from pixels, and Unicode
scalar-character offsets from byte/UTF-16 offsets. Use the returned layer IDs, check
`enabled`/`disabledReason`, and inspect after a timeout before retrying a mutation.

For example, discover editable shapes first:

```json
{"search":"shape.create","limit":1}
```

Read the entry's nested `path`, `fill`, `stroke`, conditional geometry requirements and
examples. An execute request using that contract is:

```json
{"command":"shape.create","params":{"kind":"ellipse","rect":[32,24,160,96],"fill":"#2f718c","stroke":{"width":3,"color":"#163b4a"},"name":"Ellipse"}}
```

To export the full current registry as machine-readable JSON, including every schema:

```sh
cargo run -p photocraft-cli -- commands --json > command-contracts.json
```

Schemas are cached lazily on the first metadata lookup, not rebuilt for every page or
command execution. Unit tests validate every schema against the actual draft 2020-12
metaschema, validate schema defaults/examples, compare strict-filter rules with execution,
and execute representative vector, painting and Unicode-text requests.

Browsers without WebMCP still run the editor. Integrations on the same page can explicitly
use `window.photocraft.callTool(name, arguments, {signal})`; it returns the same response as
a JavaScript object. `window.photocraft.tools` contains metadata and
`window.photocraft.webmcp` reports the chosen native API, registration count and any error.
This namespaced bridge does not impersonate or polyfill `modelContext`.

## Files, ordering and cancellation

### Browser document recovery

Browser-local recovery uses IndexedDB, independently of brush preset storage and request
receipts. With autosave enabled, dirty revisions are considered every 30 seconds (background
tabs can be throttled). Open **Browser document recovery** above the menu bar for manual
checkpoints, restore-copy selection and confirmed deletion. The same operations are available
through `photocraft_control`:

```json
{"method":"recovery.list","params":{}}
{"method":"recovery.checkpoint","params":{}}
{"method":"recovery.restore","params":{"key":"<exact key from recovery.list>"}}
{"method":"recovery.discard","params":{"key":"<exact key>","confirm":true}}
{"method":"recovery.retry","params":{}}
```

Mutations return admission, not completion. Poll `recovery.list`: require no `pending` or
`queued` key, no `error`, and the saved entry's expected `revision` or a `restored[key]`
document ID. Snapshots are complete editable `.pcraft` documents, not rendered PNGs. Restore
always opens a dirty copy with a fresh document ID and retains the source. Saving/closing a
document only automatically deletes checkpoints owned by this page; foreign snapshots need
explicit discard. The catalog is hydrated at page startup, not continuously across tabs.

Limits: 16 document pairs, 64 MiB per project, 4 KiB metadata and 256 MiB total. Replacement
and quota checks share one read/write transaction, including across tabs. Failure retains
the previous committed snapshot; nothing is silently evicted to make room. `recovery.retry`
clears the visible error for another explicit attempt, but cannot grant blocked storage.
Export your document before troubleshooting an unavailable database. Site-data clearing,
browser eviction and a different origin/profile can make recovery unavailable. A checkpoint
does not mark the document saved, verify a download, persist undo history or restore request
receipts. After a reload, inspect and reconcile the restored document before continuing edits.

### Tracked editing and safe continuation

`photocraft_execute` accepts optional paired `requestId` and `instanceId` fields. Without
them, existing synchronous/waiting behavior is unchanged. With them, the tool **immediately
returns admission/status**, while the same editor control path executes the edit in order.
Acknowledgement is not success. This avoids holding a single browser evaluation open while
a large plan runs.

First discover the current page identity:

```json
{"method":"requests.status","params":{}}
```

The result contains `instanceId`, current `tracked` count, `maxRequests` (1024), `maxBytes`
(16 MiB reserved ledger budget), `maxReplyBytes` (16 KiB) and `persistent: false`. Secure
browser UUID generation is required; failure disables tracking rather than sharing a
fallback identity. This identity is not an authentication token.

Submit one edit through `photocraft_execute`:

```json
{
  "command":"layer.new.layer",
  "params":{"name":"foreground object"},
  "requestId":"unique-plan:step-0001",
  "instanceId":"<identity returned by requests.status>"
}
```

Poll with `photocraft_control`:

```json
{
  "method":"requests.status",
  "params":{"requestId":"unique-plan:step-0001","instanceId":"<same identity>"}
}
```

Submission and query results have the same shape:

```json
{
  "instanceId":"<same identity>",
  "requestId":"unique-plan:step-0001",
  "state":"succeeded",
  "reply":{"ok":true,"result":{"layer":8}},
  "replyTruncated":false
}
```

States are `queued`, `running`, `succeeded`, `failed` and `unknown`. A normal error whose
side effects cannot be proven absent is `unknown`; it is terminal for that request ID.
Stop on either failure state, inspect and reconcile before deciding on another edit.
Queue/deadline/AbortSignal behavior still applies; aborting an admitted request does not
automatically allocate a retry. Status queries bypass pending edits and full queues.

Repeating an identical submission returns its existing status **without dispatching again**,
even when the queue is full. A different command/params under the same ID returns
`REQUEST_ID_CONFLICT`; an old page identity returns `INSTANCE_MISMATCH`. IDs are page-local,
case-sensitive, bounded to 128 UTF-8 bytes and are never automatically evicted or reset.
`LEDGER_FULL` rejects new edits before dispatch. `REQUEST_NOT_FOUND` does not itself authorize
replay; verify the saved instance and original submission. `TRACKING_UNAVAILABLE` means the
secure page identity could not be obtained. Oversized completion replies retain state but
set `replyTruncated: true` and omit `reply`; inspect object IDs/state instead of re-executing
to obtain a large result. The budget reserves reply space at admission.

This is **at-most-once dispatch within one page instance**, not persistence, an atomic batch,
or an exactly-once promise across reloads. The ledger does not reverse manual edits/undo or
track whether an earlier result remains in the current document. After user edits, undo,
navigation, document switching or recovery, reconcile the plan against the actual document.
Save the plan, stable step IDs, completed prefix and returned object IDs on the host; use
short polling windows rather than a long `page.evaluate` loop. A generic reusable workflow
is provided in [the WebMCP skill](../.agents/skills/photocraft-webmcp/SKILL.md).

### File operations

Import accepts base64 file bytes up to 64 MiB. Use the browser file picker for larger files.
Export's extension selects the format, including `.pcraft`, PSD/PSB and flat image formats.
With `download: true`, no base64 response limit applies. Export is a copy and leaves the
document's dirty state intact. `photocraft_control` with `method: "app.save"` and
`params: {path: "project.pcraft"}` downloads through the normal save path and marks a
successful save. The browser decides whether to allow downloads; keep the downloaded file.
No tool reads a host path or fetches a remote document. Linked files must be embedded or
provided through the browser. Warnings describe format-specific losses.

Editing requests are serialized, with one admitted tool dispatched per editor frame. A following call
sees completed synthetic input, screenshot or command work. There are at most 16 outstanding
requests and a bounded aggregate argument budget; normal requests are limited to 1 MiB of
JSON. Base64 import has a separate 64 MiB binary budget. Oversized/full queues fail explicitly.
An execution AbortSignal is checked before dispatch. Queued calls expire after 60 seconds
and never apply afterwards. Once work has started, a timeout/cancellation can still leave an
applied edit: inspect the document before retrying. Synchronous Wasm work cannot be interrupted
by another browser event while it occupies the main thread in the compatibility build. With
workers, registry/inspection queries and `jobs.cancel` can bypass a waiting edit, so an agent can
observe progress and cancel without waiting behind the operation it wants to stop. Edits remain
ordered. File import/export runs on a document snapshot in a worker; cancelled imports never
add their document and cancelled exports never trigger a download. The WebMCP transport adds no idle polling timer; browser recovery separately schedules its 30-second autosave checks.

## Performance and limits

Release builds keep the UI optimized for download size, compile filters, compositing, raster,
painting and CMS pixel processing at Rust optimization level 3, and run `wasm-opt -O3`.
Compressed streaming parts keep hosting limits independent of the raw module size. These
settings favor throughput; measure the actual workload before claiming a speedup.

Use release builds for timings. Browser development builds are not performance evidence.
The Performance API marks `photocraft.start` (Rust entry) and `photocraft.ready` (editor
initialized). `photocraft_inspect.result.perf` reports the selected render path and frame
timings; `memory` and `scratch` report the editor's memory accounting. Measure commands on
the same browser, machine, image, bit depth and renderer, with warmup before comparing.

The shared-memory build runs engine jobs, gradient painting, path fills/strokes, filter previews,
histograms, file decoding/encoding and CPU canvas composition on background workers. The CPU
canvas renders in cancellable bands, preserves the last texture while working, and rejects results
from old document/display/view revisions. GPU fallback keeps the existing bounded block redraw.
Workers never access the browser's GPU objects or call eframe's window-only repaint callback;
the browser thread polls only while work is outstanding and performs texture uploads/downloads.
Scratch-buffer pooling uses nonblocking cache access on Wasm: a contended lookup is a miss and
a contended return is dropped, avoiding forbidden `Atomics.wait` on the browser thread during
tile destruction. Native pooling is unchanged. Worker composition time is reported separately
as the `cpu-worker` span, not added to main-thread composite/frame timings. Old display outputs
are cancelled when no longer requested; screenshots wait for the current CPU texture to finish.
The compatibility build still executes CPU work inline. Small view/layout tasks, shape-cache
creation, interactive brush input, JSON bridge conversion and GPU uploads can still cost main-thread
time; this is not a claim that every frame meets its performance budget. Browser memory and GPU
limits are lower than a native application's; a 64-bit desktop file that exceeds Wasm memory
is not guaranteed to open. Browser documents currently have no automatic crash recovery:
save/download before closing. System printing, native plug-ins, arbitrary filesystem access,
native window management and the desktop TCP server are not browser features. Existing
PhotoCraft feature/format gaps remain tracked in [gaps](gaps.md).

### Reproducible layered drawing

`cargo run -p photocraft-web --example pelican_commands` prints a Rust-authored command plan
for an 1800 × 1200 seaside pelican riding a mint bicycle: nine named paint layers, Bezier paths,
24 spokes per wheel, scarf, beak, sea grass, flowers and paper details. It contains only registered
engine commands, not an imported flattened image or an SVG shortcut. An agent can discover
the relevant commands, then pass each `{command, params}` entry to the real
`photocraft_execute` WebMCP tool, awaiting and checking each response before the next entry.
Export `pelican-cycling.pcraft` to retain the independently editable layers and `pelican-cycling.png`
for the flattened image. The example's native regression checks its command IDs and layer count.
The browser drawing, editable-project roundtrip and responsiveness were verified on 2026-11-05
as described below; repeat that acceptance after changing the command plan or worker runtime.

Whole-image work is admitted against the browser's existing 1.5 GiB ceiling, subtracting
resident tiles (including undo data), other live reservations, and at least 256 MiB of
headroom. The former one-eighth temporary allowance rejected common 24 MP filters before
they started. This correction preserves the ceiling and still refuses work that cannot fit.

## Verified measurements, 2026-11-05

### Compatibility throughput

Local Apple Silicon Mac, Chromium 156/Ego Lite, Rust 1.97.1, release Wasm, WebGPU.
The 3 MP comparison used a 2000 × 1500 RGB/8 image filled with `#587fab`, then
`filter.noise.addNoise` with amount 15 and seed 42. One warmup, five alternating measurements
per build; our compiler processes were paused, other desktop applications remained running.
The baseline has the new agent bridge with the previous size-oriented compilation settings.

| Operation | Previous median | Optimized median | Measurement |
|---|---:|---:|---|
| Add Noise, amount 15, seed 73 | 137.7 ms | 108.1 ms | Engine command, 21.5% less time |
| Gaussian Blur, radius 12 | 187.3 ms | 150.8 ms | Engine command, 19.5% less time |
| PNG export to base64 | 388.7 ms | 403.5 ms | Complete tool call, 3.8% more time |

Both filtered PNG outputs matched SHA-256 across builds. Noise:
`072af7b562be2aaf6b2399cc26bf2a60e176a68fd542a3a773a40dacba934a56`;
Gaussian: `b179fde37a96b12a5642d27b370fb7bb604d095ca03a0ce994627897d3914708`.

The compatibility build also completed the 6000 × 4000 RGB/8 (24 MP) workflow: Add Noise
941.1 ms, Gaussian Blur radius 12 1382.5 ms (command times), PNG download 1010.5 ms
(complete tool call). These are single smoke measurements under desktop load, not p95
budgets. Before the memory-admission correction the 24 MP filter was refused. The final
compressed app in that throughput run was 14,010,857 bytes; the speed settings add about 2.2% to the compressed
baseline. The packaged site started locally in about 2.8 seconds on one initial load;
this includes localhost loading and is not a network startup guarantee.

Browser verification covered native `document.modelContext` registration of all six tools,
964 engine commands and 848 menu records, edit/undo/redo, 16-bit project roundtrip with equal
pixels, brush input, PNG screenshots, a real 32-bit `.pcraft` download, WebGL2 fallback,
and a browser with both modelContext APIs unavailable. Three malformed requests were rejected;
an aborted queued layer creation made no edit; a 20-call burst admitted 16 and rejected four.
The compatibility `navigator.modelContext` path is implemented but was not tested in a browser
that only provides that older API.

### Shared-memory workers and drawing acceptance

On the same Apple M2/Chromium 156 host, the worker build used pinned nightly-2026-08-17,
rebuilt standard-library atomics and the CPU canvas (`?cpu`). Three runs per configuration
applied Add Noise amount 20, then Gaussian Blur radius 12, on the same RGB/8 document.
The browser sampled a 10 ms interval through both edits and the following canvas work.
The gap is timer interval duration, not a frame-time or input-latency budget.

| Workflow | Compatibility median | Worker median | Largest timer-gap median, compatibility → worker |
|---|---:|---:|---:|
| 2000 × 1500 (3 MP), noise + Gaussian | 351.9 ms | 228.0 ms | 195.4 → 11.2 ms |
| 6000 × 4000 (24 MP), noise + Gaussian | 2452.0 ms | 1551.7 ms | 1415.6 → 13.7 ms |

After the scratch-pool contention fix, an additional three 24 MP runs took 1512.5, 1491.8
and 1952.8 ms, with largest timer gaps of 11.9, 12.1 and 12.7 ms respectively and no runtime
errors. During an earlier 24 MP radius-80 Gaussian, `jobs.list` replied in 21.6 ms and
`jobs.cancel` in 18.7 ms; the edit reported cancellation without committing its result.
These are local, low-sample observations, not enforced performance budgets.

The real `document.modelContext` tools completed all **518 commands** of the layered pelican
in **16.30 seconds**, with `backgroundWorkers=true` and no window/worker errors. Exporting
and reopening the 3,223,909-byte `.pcraft` preserved all **ten layers** (nine named drawing
layers plus Background). Its PNG matched the compatibility drawing and the reopened project
byte-for-byte, SHA-256 `e77b7d22100074c319517b42ece4ee101d377913cc3ff50dca97c2af569b90fa`.
The exported PNG and a screenshot of the visible editor were visually inspected against the
reference composition. No flattened image was imported to produce the drawing.

The rebuilt direct-worker app repeated the 518 commands in 15.86 seconds. The extracted
release zip then repeated them in 16.46 seconds with the CPU canvas, ten layers, no runtime
errors and the same PNG hash; its `ui.screenshot` tool returned the completed canvas.
Both subpath-hosted loader variants were exercised: an isolated page selected workers, while
a non-isolated page selected compatibility. Each exposed six tools and created, gradient-filled
and exported a 16-bit project. The release includes both payloads; its largest hosted file is
14,132,395 bytes, below the 25,165,824-byte packaging gate.
Two undos changed the finished drawing and two redos restored its PNG exactly. On the packaged
24 MP radius-80 Gaussian, `jobs.list` and `jobs.cancel` replied in 21.4 and 19.9 ms respectively;
the edit returned `cancelled` with unchanged history (93.7 ms total including the initial delay).

The first complete drawing also included a 516.9 ms timer gap during initial UI setup;
the editor attributed a 474.8 ms frame to the first named layer while its command itself took
2.1 ms. A warm 50-command rerun recorded no long tasks. Worker execution therefore does not
prove that startup, fonts, texture uploads or every interactive frame are nonblocking.
Evidence is in local `log/webmcp/main-thread-*.json`, `worker-cancel.json`,
`pelican-worker-execution.json`, `pelican-worker-roundtrip.json` and `pelican-worker*.png`.

These results do not establish universal performance or Photoshop parity. The non-isolated
compatibility build still runs CPU jobs inline. SIMD and browser document recovery remain open;
worker builds require cross-origin isolation and a browser that supports shared Wasm memory.
